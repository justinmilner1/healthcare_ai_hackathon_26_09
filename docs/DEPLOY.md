# Deploying Sweet Spot

The infrastructure is code: `/infra` is an AWS CDK app in TypeScript (design §3.6), and one stack class
produces both environments — staging (§13.2) and production (§13.3, T30). This page is how a human takes that
stack from `cdk synth` to a running deployment, and which steps only a human can do.

Owner: ops. The day-to-day operations — rollback, rotating a secret, restoring a backup, what each alarm means
— are `docs/RUNBOOK.md` (T35). This page is the first deploy and the shape of the thing.

## What the stack contains

| Resource | Why | Design |
|---|---|---|
| Amplify Hosting app, `WEB_COMPUTE` platform, one branch | Next.js SSR, auto-building on every merge to the branch | §3.1, §13.2 |
| RDS Postgres 16, encrypted, 7-day backups | the database; `force_ssl` on the server | §3.2, §10.1, §11.4 |
| S3 bucket, private, versioned, TLS-only | uploaded exports; never in the database | §3.3, §10.1 |
| KMS key `alias/sweetspot-<stage>-dexcom-tokens` | encrypts stored Dexcom refresh tokens | §4.10, §10.1 |
| SES identity + configuration set | sending, and the bounce and complaint feed | §8, §8.1 |
| Two SNS topics: `-alarms`, `-mail-events` | where alarms and delivery events go | §8.1, §11.1 |
| EventBridge Scheduler rule, every minute, and a 60-line Lambda | calls `POST /api/jobs/run` with the shared secret | §3.4 |
| 12 SSM `String` parameters under `/sweetspot/<stage>/` | the non-secret half of the configuration | §3.7, §10.6 |
| 4 log metric filters and 6 CloudWatch alarms | 5xx rate, job failures, model failures, model degraded, the tick, database storage | §11.1 |

Three things in there are deliberate and surprising, so they are worth reading before the first deploy.

**The database is reachable from outside the VPC.** Amplify Hosting's SSR compute cannot be attached to a VPC.
There is no NAT path to buy and no VPC endpoint to add: an app served from Amplify reaches its database over
the internet or not at all. Three things carry the weight instead — `rds.force_ssl=1`, so TLS is the server's
rule and not a client courtesy (§10.1); a security group that opens to **nothing** until a deployment names a
CIDR in `dbAllowedCidrs`; and a password generated by RDS into Secrets Manager that never passes through a
template or this repository. `cdk synth` prints a warning while that list is empty, because an app that cannot
reach its database builds, boots and then answers nothing. Choosing what goes in the list is the one security
decision this deploy asks of a person: an operator's own range is enough for migrations and `psql`, and
`0.0.0.0/0` is what it takes for Amplify to connect — a perimeter of TLS and a 32-character password. T30 is
where production can pay for a VPC-attached compute instead.

**Secrets are a deploy step, not a resource.** §10.6 puts them in SSM Parameter Store, and CloudFormation
cannot create a SecureString parameter at all. So the stack writes the plain parameters, and the six secret
names are a stack output and the `aws ssm put-parameter` commands below.

**CloudFormation owns the branch's environment variables; a human owns the app's.** Amplify merges the two,
with the branch winning. Everything the stack can compute — the bucket, the topics, the model, `APP_URL` — is
on the branch. The six secrets go on the *app*, by hand, once. Nothing in the stack touches those, so no later
`cdk deploy` deletes them.

## Before the first deploy

Things only a person can get:

- An AWS account, and credentials in the shell with permission to create the resources above.
- `cdk bootstrap` run once per account and region.
- A GitHub personal access token with `repo` scope, so Amplify can clone and watch this repository. Passed at
  deploy time as a `NoEcho` template parameter; Amplify keeps it after that. Pass an empty string to create
  the app unconnected and connect the repository in the Amplify console instead — the console route is also
  the one that installs the GitHub app, which is the more usual way round.
- A domain to send mail from, or one address verified in the SES sandbox.
- A decision about `dbAllowedCidrs`, as above.

Then fill in `infra/cdk.json`, under `context` → `sweetspot:staging`. Every key is public configuration; an
empty string or an empty list means "not set yet" and is ignored rather than deployed as an empty value.

| Key | What it is |
|---|---|
| `account`, `region` | where to deploy. Both empty synthesizes env-agnostic, which is what CI does. |
| `appUrl` | the public base URL once a domain points at the app. Empty means Amplify's own `https://<branch>.<appid>.amplifyapp.com`, which is a perfectly good staging URL. **Every patient and provider link is built from this** (§3.7). |
| `emailIdentity` | the SES identity: a domain, or a single address while the account is in the SES sandbox. Empty means the stack has no SES identity and the app cannot email. |
| `emailFrom` | `EMAIL_FROM`. Has to be inside `emailIdentity` or SES refuses the send. |
| `alarmEmail` | subscribed to the alarm topic. AWS sends a confirmation link that someone has to click. |
| `repository`, `branch` | the GitHub repository and the branch that is this stage. |
| `dbAllowedCidrs` | who may open a TCP connection to the database. |
| `modelBaseUrl`, `modelId` | Bedrock's OpenAI-compatible endpoint and the model id (§3.5). |

## The first deploy

```bash
cd infra
npm ci
npx cdk bootstrap                          # once per account and region
npx cdk deploy SweetSpot-staging --parameters GitHubAccessToken=ghp_...
```

The deploy prints the outputs the rest of this page needs. Read them back at any time with:

```bash
aws cloudformation describe-stacks --stack-name SweetSpot-staging \
  --query 'Stacks[0].Outputs[].[OutputKey,OutputValue]' --output table
```

### 1. Put the secrets in SSM

CloudFormation has no SecureString, so these six are a command each. `DATABASE_URL` is composed from the
endpoint in the outputs and the password RDS generated into Secrets Manager:

```bash
STAGE=staging
HOST=$(aws cloudformation describe-stacks --stack-name SweetSpot-$STAGE \
  --query "Stacks[0].Outputs[?OutputKey=='DatabaseEndpoint'].OutputValue" --output text)
SECRET=$(aws cloudformation describe-stacks --stack-name SweetSpot-$STAGE \
  --query "Stacks[0].Outputs[?OutputKey=='DatabaseSecretArn'].OutputValue" --output text)
PASS=$(aws secretsmanager get-secret-value --secret-id "$SECRET" --query SecretString --output text \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["password"])')

put() { aws ssm put-parameter --name "/sweetspot/$STAGE/$1" --type SecureString --value "$2" --overwrite >/dev/null; echo "set $1"; }

# sslmode=require is not optional: the server refuses a plaintext connection (§10.1).
put DATABASE_URL "postgresql://sweetspot:$PASS@$HOST:5432/sweetspot?schema=public&sslmode=require"
put AUTH_SECRET "$(openssl rand -base64 32)"     # §5.1, signs the provider session cookie
put JOBS_SECRET "$(openssl rand -hex 32)"        # §3.4, what the minute schedule sends as a bearer token
put OPENAI_API_KEY "<Bedrock API key>"           # §3.5; without it the app runs scripted (§11.3)
```

`DEXCOM_CLIENT_ID` and `DEXCOM_CLIENT_SECRET` are the same shape and can wait: with neither set, uploads work
and the Dexcom connect button says it is not configured (§9.2, `docs/DEXCOM.md`).

Check the set with `npm run config:check` against those values locally, or let the Amplify build do it — the
build spec runs `npm run config:check -- --production` and fails the deploy if something required is missing
(§3.7).

### 2. Give the app the same six values

The SSR compute reads its environment from the Amplify app, and the build reads SSM. Set the six on the app
once — Amplify console → the app → *Hosting* → *Environment variables*, at app level, not branch level — or:

```bash
APP_ID=$(aws cloudformation describe-stacks --stack-name SweetSpot-staging \
  --query "Stacks[0].Outputs[?OutputKey=='AmplifyAppId'].OutputValue" --output text)
aws amplify update-app --app-id "$APP_ID" --environment-variables \
  DATABASE_URL="...",AUTH_SECRET="...",JOBS_SECRET="...",OPENAI_API_KEY="..."
```

`update-app` replaces the app's whole variable list, which is safe precisely because the stack keeps nothing
there — but it does mean listing all six in one call. Never put them at branch level: that list *is* managed
by CloudFormation and the next `cdk deploy` would overwrite it.

### 3. Open the database

Add the CIDR you decided on to `dbAllowedCidrs` in `infra/cdk.json` and `npx cdk deploy` again. Then, from
inside that range:

```bash
psql "$(aws ssm get-parameter --name /sweetspot/staging/DATABASE_URL --with-decryption --query Parameter.Value --output text)" -c 'select version()'
```

Migrations do not need this: the Amplify build runs `npx prisma migrate deploy` from the build container.

### 4. Verify the SES identity and the alarm subscription

- A domain identity prints DKIM CNAME records to add to DNS; an address identity sends a confirmation link.
  Until one of those happens, SES refuses every send and `notify.invite` jobs fail (visible on the audit page
  and on the `job-failed` alarm).
- `alarmEmail` gets a *Subscription confirmation* mail from SNS. Unconfirmed means no alarm reaches anybody.

### 5. Connect the repository and let it build

With a token passed at deploy time the branch is already watched; otherwise connect the repository in the
Amplify console. Either way the build runs: `npm ci`, then this stage's parameters out of SSM into
`.env.production`, then `npx prisma migrate deploy`, then the §3.7 config gate, then `npm run build`.

### 6. Check it

```bash
APP_URL=$(aws ssm get-parameter --name /sweetspot/staging/APP_URL --query Parameter.Value --output text)
APP_URL=$APP_URL npm run health:check     # §11.2: database, uploads bucket, model gateway
```

A green health check and a signed-in provider page is a working deployment. Seeding a demo practice is T32.

## Every deploy after the first

§13.2: a merge to the branch is a deploy. Amplify rebuilds, the build runs the migrations and the config gate,
and a failure leaves the previous version serving. Infrastructure changes are `cdk deploy` by a human —
`npx cdk diff SweetSpot-staging` first, which is the only honest way to see what a stack edit will do.

Production (§13.3) deploys from tagged releases with migrations as a pre-deploy step and a rollback that is a
redeploy of the previous tag. That is T30, and it is a second instance of this same stack class.

## The alarms

All six publish to the `-alarms` topic. The first four read the app's own JSON log lines (§10.3, §11.1) through
metric filters, which is only possible because those lines carry no names, no phone numbers and no message
text — a log line is `{"time","level","event","requestId","route","status",…}` and nothing else.

| Alarm | Fires when | Means |
|---|---|---|
| `http-5xx` | ≥ 5 lines with `status >= 500` in 5 minutes | the app is failing requests |
| `job-failed` | any `job_failed` in 15 minutes | a job used up its three attempts: an invite, a summary or a deletion did not happen |
| `model-failures` | ≥ 10 `llm_call_failed` in 15 minutes | the model gateway is timing out or erroring (§3.5) |
| `model-degraded` | any `llm_circuit_opened` in 15 minutes | the circuit is open: everyone is reading scripted replies (§6.3, §11.3) |
| `jobs-tick-errors` | ≥ 5 Lambda errors in 15 minutes | nothing is draining the queue — a wrong `JOBS_SECRET`, or the app is down |
| `db-storage` | less than 2 GiB free | storage autoscaling has not kept up |

## Checking the stack without an AWS account

`bash scripts/infra-check.sh` — part of `scripts/agent-check.sh`, so CI and both routines run it on every pull
request (§12.4). It installs `/infra`, audits its dependencies (§10.8), typechecks, runs the stack's own unit
tests, and runs `cdk synth`. No credentials, no Docker: nothing in the stack does a context lookup, and the
one Lambda is dependency-free JavaScript, so there is nothing to bundle.

Two warnings are expected there and are not failures:

- `PubliclyAccessible: RDS instance has PubliclyAccessible set to true` — the Amplify VPC limit above.
- `dbAllowedCidrs is empty for staging` — only while no deployment has named a CIDR. It disappears as soon as
  `cdk.json` has one, and it is the stack telling you the app would not be able to connect yet.

## Known edges

- **The app log group.** The alarms attach metric filters to `/aws/amplify/<appId>`, so the stack declares that
  log group rather than waiting for Amplify to create it on the first request. If an earlier deploy of the same
  app already created it, CloudFormation will refuse to create it again: import it
  (`cdk import`) or delete the empty group and deploy again.
- **`cdk destroy` keeps your data.** The bucket, the KMS key and the staging database's final snapshot are
  retained on purpose. Deleting patient data is a staff action in the app (§10.5), not a stack action.
- **Not in this stack yet.** The production stack and tagged releases (T30), the demo practice flag (T32), the
  backup restore drill (T33), the compliance checklist (T34) and the runbook (T35) are their own tickets.
